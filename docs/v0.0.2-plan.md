# Luma v0.0.2 implementation plan

## Scope

Load current title, artist, and playback state when Luma opens. Keep the interface in sync with playback changes from Music, media keys, Luma, and natural advancement. Show distinct playing, paused, stopped, and unavailable states. Preserve Previous, Play/Pause, Next, and manual Refresh. Add only the development bundle metadata needed to verify Automation if the current launch path cannot establish Luma's own consent identity. Artwork, seeking, volume, library, playlists, search, full interface redesign, MiniPlayer, menu bar, global shortcuts, and public distribution belong to subsequent milestones.

The repository audit verifies compilation and scripting terminology. Runtime behavior and the timing values below are implementation hypotheses until tested on Monterey. See the [repository audit](repository-audit.md).

## 1. Establish the interactive baseline

- Build the current revision with `swiftc` into a temporary location. Launch it from the intended interactive user session and record the behavior of transport buttons and Refresh before making changes. Use a local track and an Apple Music stream. Include a cloud-library item if the reference account exposes one.
- Use an isolated diagnostic listener to record whether `com.apple.Music.playerInfo` arrives for play, pause, next, previous, natural advancement, and media keys. Repeat with Luma inactive. Compare foreground delivery to a per-observer `.deliverImmediately` configuration and measure useful event coverage. If the event is absent or unreliable, use lifecycle triggers and fallback reads, then measure normal latency under that path.
- Check Music open with playback, open without a current item, paused, and closed. Confirm bundle-ID addressing and Music-running detection via `NSWorkspace`. If the target quits between the running check and a scripted read, test whether the operation can relaunch Music. If it can, require a passive target scoped to the running process with a launch-safe transport before sign-off.
- Identify the actual Automation prompt owner when running from a terminal versus opening a development bundle in Finder. If the current executable does not attribute consent to Luma, create a minimal CLT-built development `.app` with a stable bundle ID and `NSAppleEventsUsageDescription` before testing denied and allowed flows. Validate the plist and recheck after rebuilding at the same location. Respect system consent and keep the existing direct compilation path. [Apple Events usage description](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription)

## 2. Add typed, asynchronous Music operations

- Update `MusicService.swift` to offer asynchronous snapshot and transport operations. Keep `NSAppleScript` creation, optional reuse, execution, and descriptor decoding on one serial queue. Return Swift values to the caller. Use short, explicit AppleScript timeouts, initially around three seconds per Apple event, and verify behavior under a slow or unresponsive Music application. Audit queue residency and responsiveness while the system consent prompt is displayed. [Threading guidance](https://developer.apple.com/forums/thread/759287) · [Timeout behavior](https://developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/reference/ASLR_control_statements.html)
- Read `player state` and resolve `current track` once in the snapshot script. Return a typed positional descriptor list with required state and optional title and artist. Include an optional track identity if the spike confirms a stable read for the supported sources. Keep all metadata tied to the same track object and validate rapid changes. If references resolve to the new `current track` mid-read, verify identity before publishing and use a bounded recovery read on mismatch. A single script invocation can still send more than one event.
- Distinguish Music not running, no current track, transient transition, permission denied, timeout, and malformed reply. Map known errors by validated AppleScript numbers, including `-1743` for Apple Events permission denial and `-1712` for timeout. Confirm how the Monterey version signals missing `current track`. Preserve an unknown error category and log only diagnostic codes and timing by default.
- Use enum cases for playing, paused, stopped, fast forwarding, rewinding, and unknown. Preserve an optional track independently of state so pause keeps metadata and a stream can be playing with no readable track. Map empty properties independently. A previous snapshot may remain visible during a transient failure if clearly marked stale. Clear it on a confirmed missing track, Music termination, or permission denial.
- Keep transport commands fixed and expose structured success or failure. Send the selected command once. After a timeout, read actual state when possible since Music may have applied the command after Luma stopped waiting.

## 3. Coordinate refresh and lifecycle

- Introduce `PlaybackModel.swift` as `@MainActor` and `ObservableObject`. Let `LumaApp.swift` create it once using `@StateObject` and share it with `ContentView`. Store the snapshot and connection state together so observers can never render a new title with the old artist.
- Make startup idempotent across windows. Subscribe once to Music launch and termination using `NSWorkspace`. Refresh on startup, Music launch, Luma activation, wake from sleep if useful in the spike, manual Refresh, and transport completion. Cancel delayed work and remove observer tokens when observation ends.
- If validated, turn Music distributed notifications into refresh hints. Ignore sender data and coalesce bursts for around 150–250 ms, with bounded delay during continuous bursts. Read immediately on explicit Refresh and after a transport command. Apple documents that delivery can lag or drop and that AppKit manages suspension. [Distributed notifications](https://developer.apple.com/documentation/foundation/distributednotificationcenter?language=objc)
- Allow one read at a time and keep at most one pending read. Skip redundant periodic work if a recent read already covered it. Reconcile about every 15 seconds while Music is running and Luma has an open playback window, including when paused or inactive. Include timer tolerance around two seconds and schedule from the last read so triggers do not create redundant polls. Stop periodic reads when no playback window is open, Music terminates, or Automation is denied. Resume on a documented lifecycle event or an explicit retry. Repeated transient failures can back off to 30 and then 60 seconds while exposing a stale status. These are proposed starting values to tune from measurements.
- Give transport priority over a pending background refresh. Keep one command in flight and temporarily disable transport buttons while it is being sent. Invalidate any read from before a command or Music termination using a generation counter. Keep the last confirmed state until a post-command read completes. If a new track command returns unchanged or temporarily empty metadata, allow up to two read-only retries around 300 ms and 1 second after the first read. Cancel those retries when newer work supersedes them or the expected transition is confirmed. At a queue boundary, accept the verified unchanged state after the retry budget.
- When Music is closed, show an unavailable state and leave it closed during startup, automatic refresh, and manual Refresh. If the existing Play/Pause behavior opens Music, preserve it as a deliberate user action after checking the baseline. Avoid repeatedly requesting Automation after denial. Display recovery guidance for Monterey's Security & Privacy → Privacy → Automation when consent has been denied, and permit explicit Refresh to recheck after the setting changes.

## 4. Connect the existing interface

- Replace separate view-local title and artist with one snapshot from the shared model. Render Play for paused or stopped playback, Pause for active playback, and a neutral control state while availability is unknown. Keep the artwork placeholder for this milestone.
- Label icon buttons for accessibility. Keep Refresh available for explicit recovery and present concise messages for closed Music, no current track, denied Automation, and a failed command. Preserve the last usable metadata during brief transitions and distinguish stale state when Music is slow.
- Build after the service change, after the model integration, and after the view and launch changes. Record `swiftc --version`, the deployment target, and the verified launch path with the release evidence. If SwiftPM remains broken, use a small direct-compiled test harness for targeted state tests and keep the manifest repair out of the milestone.

## 5. Verify before release

| Scenario | Acceptance check |
| --- | --- |
| Startup, playback state, and metadata | Open Luma during play, pause, stopped playback, and with Music closed. Display the correct state. Pause preserves the current title and artist. A closed Music app stays closed during passive refresh. |
| Existing commands | Exercise Previous, Play/Pause, Next, and Refresh. Each accepted playback click sends one command. Test both queue edges and rapid input. Confirm the visible state against Music. |
| External changes | Exercise Music controls, hardware media keys, and natural progression with Luma active and inactive. Sample at least ten representative transitions and record latency and source type. With usable notifications and a responsive Music app, target visible convergence within two seconds. |
| Fallback and recovery | Disable the hint listener deliberately. With one open window and responsive Music, target convergence within 20 seconds, inclusive of timer tolerance. Exercise Music quit and relaunch, sleep and wake, and repeated transient failures. Backoff timing is measured separately. |
| Permissions and errors | Exercise initial consent, denial, explicit retry after permission changes, missing track, missing metadata, malformed reply, and a simulated slow Music response. The window stays responsive, a timed-out transport command is sent once, and stale data never overwrites state from a newer command or Music instance. |
| Content and identity | Test local, cloud-library, and subscription streaming where available, including transitions between tracks with similar names. Record unavailable content categories and verify that title and artist never come from different tracks. |
| Windows and automation rate | Compare one and two open windows. With healthy Music and no trigger traffic, expect about four snapshot invocations per minute at steady state and zero in closed-Music, denied, or no-window states. Count snapshot invocations separately from underlying Apple events. |
| Responsiveness and footprint | Record CPU, resident memory, snapshot counts, and latency using the same reference Mac, track sources, and observation windows. Sample the baseline and candidate with Music closed, paused, playing, and under a burst of skips. Use Activity Monitor or CLT-compatible tooling and include build type and sample duration. Decide whether the cadence or implementation needs tuning from the results. |

Add focused regression coverage for descriptor decoding and refresh ordering with controllable service replies. Cover a late read after a command, a late read after Music quits, coalescing, and a denied-permission retry. Keep real Music and Automation tests manual because they need playback fixtures and a GUI session.

Release after the native x86_64 build succeeds with the macOS 12.0 target and the Monterey playback, permission, and lifecycle checks pass. Record actual timings and known source coverage in the release notes. Keep generated outputs outside tracked `build/Luma`. Schedule removal from version control and `.gitignore` cleanup as a separate maintenance change.

## Implementation decisions

- `MusicService` uses public Apple Events for Music's scripting commands. Addressing the running Music process by PID prevents a passive snapshot from relaunching Music during a quit race. The service validates the target and waits for replies on a serial queue. [Apple Event descriptors](https://developer.apple.com/documentation/foundation/nsappleeventdescriptor)
- Each snapshot reads player state and requests the current track's properties as one record. Title, artist, and optional track identity come from that same record. Player state is a separate Music reply. The service retains only the selected fields and logs operation type, time, and error codes.
- The shared model listens for distributed notifications as hints and reconciles from its last read. The development bundle has a stable bundle identifier, a usage description, and an ad hoc signature. See the [build and test commands](../README.md).

## Verification on Monterey

- Swift 5.7.2 built the Intel executable with a macOS 12.0 deployment target. The development bundle passed plist and signature validation, and all eight direct-compiled playback checks passed.
- On macOS 12.7.6, the launched bundle successfully read Music at startup. A synthetic distributed notification triggered a read with the listener enabled. With the listener disabled, the synthetic notification caused no immediate read and the fallback read completed approximately 15 seconds after the last successful read.
- Genuine Music notifications, transport behavior across real content sources, the interactive Automation denial flow, and the CPU and memory comparison remain part of release acceptance. The smoke test exercised snapshots without changing Music playback or library data.

## Desktop scope update

The desktop implementation brings artwork, progress, seeking, Music volume, and read-only library and playlist browsing into v0.0.2. The app retains process-addressed Music events. The only launch paths are an explicit Connect or Play action when Music is closed. The launch configuration suppresses activation and requests a hidden launch. [NSWorkspace launch options](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration)

Artwork is loaded off the UI thread when the current track changes and is decoded to a thumbnail with a 600-pixel maximum edge. The progress bar interpolates the last Music position using a monotonic clock while playback is active. Seek and volume writes happen on slider release during pointer drags. Songs and playlist tracks are loaded on demand in pages of 60, with positions resolved in the selected Music collection. [Apple Event range specifiers](https://developer.apple.com/documentation/coreservices/formrange?language=objc)

The Monterey desktop build passed signature validation and ten direct-compiled checks. A live Music session returned a paused track, artwork, position, volume, and real playlist records. The backend read both pages of a 112-track playlist and a separate single-track final page. Music confirmed seek and volume commands when sent the track's existing values while paused. The Songs collection was empty in the test library, so the populated pagination check used playlists. Background launch from a closed Music process was covered at model level, with desktop focus behavior still to confirm in that scenario.
